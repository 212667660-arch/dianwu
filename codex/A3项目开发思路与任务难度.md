# A3 项目开发思路与任务难度

> 项目：基于大模型的个性化资源生成与学习多智能体系统开发
> 目标：构建一个可打包为 Windows 桌面程序的个性化学习助手。

## 一、项目整体思路

系统采用“用户输入学习需求 → 画像 Agent 分析 → 资源生成 Agent 创作 → 后端组织结果 → 前端展示”的主流程。

核心原则：

- 先完成单用户、单主题、单次生成的 MVP，再扩展历史记录和复杂协作。
- Agent 之间只传递结构清晰、可读的纯文本或 Markdown，方便调试和展示。
- 后端负责流程编排、模型调用、数据校验和流式输出，前端负责交互和渲染。
- 所有模型调用都通过统一适配层，避免业务代码直接依赖某个模型服务商。
- 每个 Agent 都要有明确输入、输出和失败处理方式，不能只依赖自然语言描述。

## 二、系统模块划分

### 1. API 接口层

职责：接收前端请求、校验参数、返回普通结果或流式结果。

建议接口：

- POST /api/diagnosis：提交诊断对话，生成学习者画像。
- POST /api/resources：根据画像和学习主题生成学习资源。
- POST /api/resources/stream：以流式方式返回生成内容。
- GET /api/health：检查服务和模型连接状态。
- GET /api/history：读取用户的历史画像和学习资源。

### 2. 模型调用适配层

职责：封装混元大模型的请求、超时、重试、错误信息和流式响应。

需要完成：

- 统一模型调用函数或类。
- 支持普通请求和流式请求。
- 读取环境变量中的 API Key 和模型配置。
- 处理网络失败、模型限流、返回格式错误和超时。
- 记录必要的请求日志，但不要记录敏感信息。

### 3. 学习者画像 Agent

职责：根据简短对话分析学习者的基础水平、薄弱点、目标、偏好和认知层次。

画像至少包含：

- 学习主题和学习目标。
- 已掌握知识点。
- 薄弱或待确认知识点。
- 学习风格倾向，例如图示型、文字型、案例型或练习型。
- 认知层次，例如了解、理解、应用、分析。
- 推荐难度和推荐学习顺序。
- 画像可信度以及需要继续追问的问题。

### 4. 资源生成 Agent

职责：依据学习者画像，生成个性化学习笔记、分层练习题和详细解析。

资源建议包含：

- 学习目标。
- 个性化知识讲解。
- 重点和易错点。
- 基础题、提高题和挑战题。
- 每道题的答案、解题过程和错误原因。
- 下一步学习建议。

### 5. Agent 编排层

职责：控制多个 Agent 的调用顺序、传递上下文、校验结果并处理失败。

推荐流程：

1. 接收用户主题和初始对话。
2. 调用画像 Agent 生成画像文本。
3. 检查画像是否包含必要字段。
4. 将画像、主题和资源要求传给资源生成 Agent。
5. 检查资源是否包含笔记、题目和解析。
6. 返回最终结果，或将生成过程通过流式接口推送给前端。

### 6. 数据存储层

第一版可以使用 SQLite，保存用户画像、诊断记录、学习资源和生成时间。后续再考虑 PostgreSQL。

建议数据表：

- learner_profiles：学习者画像。
- diagnosis_sessions：诊断对话记录。
- learning_resources：生成的学习资源。
- generation_logs：模型调用和错误记录。

## 三、分阶段开发任务

### 阶段 0：需求和接口设计（难度：低）

需要完成：

- 明确 MVP 只支持单用户和单学习主题。
- 确定画像字段、资源字段和 API 请求响应格式。
- 设计 Agent 之间的纯文本协议。
- 确定普通响应和流式响应的格式。

阶段产物：接口草图、字段说明、Agent 输入输出示例。

### 阶段 1：FastAPI 后端骨架（难度：低）

需要完成：

- 创建 Python 虚拟环境和依赖文件。
- 创建 FastAPI 应用入口。
- 增加路由、配置、日志和异常处理目录。
- 增加 /api/health 健康检查接口。
- 增加统一响应格式。

阶段产物：后端可以启动，健康检查可以访问。

### 阶段 2：混元模型适配（难度：中）

需要完成：

- 配置 API Key 和模型名称。
- 实现普通模型调用。
- 实现流式模型调用。
- 增加超时、重试和错误转换。
- 用一个简单测试请求验证模型连接。

阶段产物：通过统一接口可以调用混元模型。

### 阶段 3：画像 Agent（难度：中）

需要完成：

- 编写画像 Agent 的系统提示词。
- 设计纯文本输出格式。
- 将模型输出转换为后端可使用的字段。
- 增加缺字段和格式错误处理。
- 编写至少三组不同学习者测试样例。

阶段产物：输入简短对话后，可以生成稳定的学习者画像。

### 阶段 4：资源生成 Agent（难度：中）

需要完成：

- 编写笔记、练习题和解析生成提示词。
- 支持基础、提高、挑战三种难度。
- 将学习者画像注入资源生成上下文。
- 增加内容完整性检查。
- 确保输出适合 Markdown 或纯文本渲染。

阶段产物：根据同一主题的不同画像生成不同资源。

### 阶段 5：多智能体编排（难度：高）

需要完成：

- 实现画像 Agent 到资源生成 Agent 的上下文传递。
- 设计 Agent 状态和任务状态。
- 支持单个 Agent 失败后的错误返回或有限重试。
- 保存每个阶段的中间结果，便于调试。
- 设计可扩展的 Agent 注册方式。

阶段产物：两个 Agent 可以按照固定流程协作完成一次资源生成。

### 阶段 6：流式输出（难度：高）

需要完成：

- 选择 Server-Sent Events 或 WebSocket。
- 将 Agent 执行状态和模型文本分片发送给前端。
- 区分诊断阶段、生成阶段、完成和错误事件。
- 处理客户端断开和服务端取消任务。
- 确保流式输出不会破坏 Markdown 内容。

阶段产物：前端可以实时看到诊断和资源生成过程。

### 阶段 7：持久化和历史记录（难度：中）

需要完成：

- 建立 SQLite 数据库。
- 保存诊断会话、画像和学习资源。
- 增加历史记录查询接口。
- 增加基本的数据清理或删除能力。
- 处理数据库异常和重复请求。

阶段产物：关闭应用后，历史学习内容仍然可以读取。

### 阶段 8：测试、打包和展示（难度：高）

需要完成：

- 编写模型适配层和 Agent 编排层的单元测试。
- 编写 API 集成测试。
- 增加无 API Key、模型超时、格式错误等演示场景。
- 配合 Electron 完成启动和接口地址配置。
- 打包 Windows .exe，并验证用户无需手动配置 Python 环境。
- 准备项目演示脚本、系统架构图和技术说明。

阶段产物：可以在评审电脑上启动并完成一次完整演示。

## 四、任务难度总表

| 任务 | 难度 | 原因 | 推荐模型 |
| --- | --- | --- | --- |
| 项目目录和 FastAPI 骨架 | 低 | 主要是工程初始化 | Luna/Terra |
| 配置和健康检查接口 | 低 | 逻辑简单，适合快速完成 | Luna |
| 混元模型普通调用 | 中 | 需要处理鉴权、错误和超时 | Terra |
| 混元模型流式调用 | 高 | 涉及异步、断开和事件格式 | Sol/Terra |
| 画像 Agent 提示词和输出 | 中 | 需要稳定结构和内容质量 | Terra |
| 资源生成 Agent | 中 | 需要控制难度、格式和完整性 | Terra |
| 多 Agent 编排 | 高 | 涉及状态、上下文和失败恢复 | Sol |
| SQLite 历史记录 | 中 | 需要数据模型和接口设计 | Terra |
| 前后端流式联调 | 高 | 涉及协议、渲染和异常场景 | Sol/Terra |
| Electron Windows 打包 | 高 | 涉及环境、路径和进程管理 | Sol/Terra |
| 项目文档和演示材料 | 低 | 主要是整理已有成果 | Luna |

## 五、建议的 MVP 范围

为了尽快得到可演示版本，第一轮只实现以下内容：

1. FastAPI 启动和健康检查。
2. 一个统一的混元模型调用适配器。
3. 画像 Agent。
4. 资源生成 Agent。
5. 一个同步的完整生成接口。
6. Markdown 文本结果返回。
7. 最少三组测试样例。

完成 MVP 后，再依次加入流式输出、SQLite 历史记录、前端联调和 Electron 打包。

## 六、关键风险和应对方法

- 模型输出格式不稳定：使用固定模板、字段检查和有限重试。
- Agent 之间职责重叠：明确画像 Agent 只负责分析，资源 Agent 只负责生成。
- 流式输出难调试：先完成同步接口，再增加流式接口。
- API Key 泄露：只从环境变量读取，不写入代码和提交文件。
- 生成内容质量不稳定：准备固定测试集，并人工检查典型输出。
- 打包后找不到配置文件：统一使用相对路径和可配置的应用数据目录。
- 单次任务耗时过长：增加执行阶段提示、超时、取消和错误反馈。

## 七、最终验收标准

- 用户可以输入学习主题和简短自述。
- 系统可以生成结构化学习者画像。
- 系统可以根据画像生成个性化笔记、分层练习题和解析。
- 两个 Agent 的职责和调用过程清晰可解释。
- 生成内容可以以纯文本或 Markdown 正常展示。
- 模型超时、无效输出和服务不可用时有明确错误提示。
- 后端 API 有基本测试，项目可以稳定启动。
- 最终程序可以打包为 Windows 桌面应用并完成现场演示。

## 八、推荐执行顺序

先做阶段 0 和阶段 1，确认接口和项目能启动；然后完成阶段 2，确保模型调用可靠；接着分别实现画像 Agent 和资源生成 Agent；两者单独稳定后再做多 Agent 编排；最后加入流式输出、历史记录、前端联调和 Electron 打包。

当前默认开发策略：后端日常实现使用 Terra；复杂架构和多 Agent 编排使用 Sol；文档、注释和简单脚本使用 Luna。
